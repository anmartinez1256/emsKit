# cg28 = 85dc48c on speed-m5-gpu (v0.37.0-34-g85dc48c): the Metal diamond engine (--engine=metal-diamond) picks its
# tiling at run time. Apple M5 (10 GPU cores), macOS 27.0.1; a shared Mac, so every number carries the other processes'
# CPU and GPU use during the runs (bench/usage.py). Library: ~/opt/openEMS-dev/snap/cg28 (built as dev28b).
#
# What it does (FDTD/metal/engine_metal_diamond.mm): SetupGPU builds four tilings, K time steps per block and
# mountains M / valleys V wide in x and y: K=4 8,8 (the old default), K=4 12,8, K=3 8,6, K=3 6,6. In the tile and K
# sweep of cg23 (faster of two runs per setting, not paired; results/diamond_engine_cg24_cg27_2026-11-04.txt section
# 8) four models ran best with one of these and the SMA launch and the patch tutorial with a K=2 tiling, 0.3 % and
# 1.2 % above the best of the four; in the K sweep of cg27 (results/fused_sweep_k1_2026-11-04.txt section B) K=4 8,8
# beat K=2 4:4 and K=1 on all six. K=2 tile 6:4, the SMA's best in the paired runs of cg24 (x1.132 over K=4 8,8; K=3
# 8,6 x1.065), is not among the four and was not timed after cg24. (Corrected 2026-11-05: this paragraph first said
# that every model ran best with one of the four in the sweeps of cg23 and cg27.) Each tiling has its tile buffers,
# threads per tile and a copy of the extension words followed by its per-tile lists (excitation runs, lumped RLC
# lists, dispersive runs); the extension floats and the state are shared. While tuning, IterateTS gives its command
# buffers the tilings in turn (half batches of 32 steps, at most two buffers in flight), keeps per tiling the least
# GPU time per step (GPUEndTime - GPUStartTime) of 4 timed buffers, then runs the fastest and releases the other
# tilings' buffers. Timed are full batches and whole IterateTS calls; the short last buffer of a call and the first
# buffer of the run (buffer mapping, GPU warm-up) run the first tiling and do not take a turn. Every tiling gives
# every value the same operations in the same order (only independent cells change their order), so the fields do not
# depend on the choice. Knobs: OPENEMS_DIAMOND_TUNE=n timed buffers per tiling (default 4), 0 = K=4 8,8 without
# tuning; OPENEMS_DIAMOND_K, OPENEMS_DIAMOND_TILE and OPENEMS_DIAMOND_TIMING=2 fix one tiling as before; verbose > 0
# or OPENEMS_DIAMOND_TIMING=1 print the choice.
#
# 1. Identity
# - scripts/checks/diamond_check.sh on cg28: 72 of 72 identical: the 54 comparisons of cg27 plus, per box spec, a tuned
#   run with OPENEMS_DIAMOND_BATCH=8 (the tuning ends within the run, after 129 steps, then K=3 6,6 or 8,6 on these
#   41-43^3 boxes) and a run with the default batch (the tilings change every command buffer for most of the run).

# On the notch tutorial and patch x5 the default tiling is the best one; there the tuning (about 600 steps with the
# other tilings in turn) costs 0.4-0.5 % of these short runs and nothing measurable in real runs (34k-190k steps).
#
# 4. The first version (dev28a, 2026-11-04 21:28-21:35, others' CPU 2.5-5 cores, GPU 2-4 %) gave every command buffer
#    the next tiling, including the short last buffer of each IterateTS call, which is not timed. When the calls are
#    a whole number of rounds long (notch x3: 258-step calls = eight buffers, the eighth short), the same tiling got
#    the short buffer every call, so the tuning took 936 instead of 614 steps on notch x3 (552-1368 on the six models),
#    and other call lengths could starve a tiling for the whole run (an independent review of the code found the same).
#    Paired against cg27 it gave SMA x1.081, GCPW x1.106, notch x3 x1.024, patch tutorial x1.082, notch tutorial
#    x0.993, patch x5 x0.997 (the best fixed tiling: x1.085, x1.101, x1.060, x1.075). cg28 times only full batches and
#    whole calls and lets only those take a turn.
#
# 5. Independent review (three read-only reviewers with different lenses, each finding checked by two refuting
#    verifiers, 2026-11-04 21:31-22:00, on the first version's diff): two reviewers found the round-robin problem of
#    section 4 (confirmed for the first version, already fixed in cg28: the verifiers traced the cg28 rule and found that
#    no call pattern can starve a tiling). The third point, that on the patch tutorial (38-step calls) the choice rests
#    on three 32/33-step samples per tiling because its 2-6-step end-criterion calls use a fourth slot, was refuted by
#    both verifiers as an effect on the choice: a short buffer costs more per step, so it can never make a slower tiling
#    win, and every cg28 run picked the fastest tiling. No change.
