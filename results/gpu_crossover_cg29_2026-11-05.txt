# GPU against CPU by grid size: snapshot cg29 (1620939), Apple M5 (4 P + 6 E cores, 10 GPU cores), macOS 27.0.1, 2026-11-05.
# The question (the author, 2026-11-05): at how many cells does the GPU engine become faster than the CPU engine, and why is
# it slower below that? Drawn in paper/figures/fig_crossover.py; text in paper/sec_gpu.tex ("Where the GPU overtakes the CPU").
#
# Method. Three bench models (bench/models.py) at several mesh scales: the patch antenna of the patch tutorial (scale 1
# = the patch tutorial, 0.104 M cells; scale 5 = patch x5, 7.863 M), the notch filter of the notch tutorial (scale 1 =
# the notch tutorial, 0.270 M; scale 3 = notch x3, 5.247 M) and the toolkit's GCPW line (scale 1 = the GCPW line of the
# tables, 0.242 M; its scale multiplies the cell size, so a smaller scale gives more cells). Each point is one paired,
# interleaved run of bench/abtest.py with 4 rounds; in every round the four configurations run in turn: c0 the
# multithreaded engine at 8 threads, c1 at 4 threads, c2 the metal-diamond engine, c3 the metal-diamond engine with
# OPENEMS_DIAMOND_TIMING=1 (GPU busy time per IterateTS call; c3/c2 over the points: see the checks). Every run waited
# (at most 1800 s) until the other processes used at most 150 % CPU and 10 % of the GPU, and was run again when they
# used more of either during it, up to 3 times (--quiet 150 --quiet-max 1800 --run-redo 3; the discarded runs are the
# raw output's "# redo" lines; one run, notch filter s1 r0 c1, went ahead after the 1800 s with the others at 774 %
# CPU, in a round that is left out). A round "kept after 3 redos" with a loaded run is left out of a point's medians
# when at least two clean rounds remain ("rounds": "3 of 4"; "N loaded" = fewer remained, so they are used). Steps:
# enough for a time loop of about 2 s on the small grids (36 500 on the patch tutorial), 3 000 on the large ones; the
# models' probes and dumps as in the bench (the patch's nf2ff dumps end an IterateTS call every 31 steps at scale 1).
# Passes (scripts/gpu_crossover/sweep.sh runs the same list in one go): 10:24-16:15 the first 21 points; 16:17-16:33 the
# GCPW line at 3.2 and 5.1 M cells and patch scales 2.5 and 3 again (their first pass had 3 of 4 rounds loaded; the
# table uses the re-runs, the first pass is in the raw output); 16:33-16:37 the run-length check (section 5);
# 16:37-16:42 the patch at 2.9 M and the GCPW line at 2.4 M cells, inside the two gaps around the crossover. Load: other
# sessions' builds and solvers, load average 1.7-17.5 at the start of a point; in the runs used the others took 0.5-1.3
# cores and 1-5 % of the GPU (median of a point; at most 1.5 cores and 9 %).
#
# Columns. MC/s = million Yee cells per second of the time loop (openEMS's own figure), median [min-max] over the rounds
# used; "*" marks the CPU thread count with the higher median (8 threads at every point). GPU / CPU best = median
# [min-max] of the per-round ratio of c2 to that thread count. From the c3 runs (median over the rounds used): GPU busy
# = GPU busy time / time loop; gaps = time inside IterateTS with the GPU idle (starting and finishing the call's command
# buffers); outside = time loop outside IterateTS (probes, dumps and the rest of the main loop, on the CPU); GPU-only =
# cells x steps / GPU busy time, the GPU's rate while it works; steps/call; GPU ms/call and idle ms/call = GPU busy and
# idle time per IterateTS call (idle = time loop - busy; on the large grids, with 4-28 calls per run, it includes the
# start and end of the loop); tiling = the tuner's choice (K, M,V) in the c3 runs used, with counts where they differ
# (the plain GPU runs do not report theirs); tiles/dispatch = tiles in one dispatch of each tiling listed, fewest (MM)
# to most (VV), x threads per tile, from a verbose 100-step run of the point; others = the other processes' CPU in cores
# and GPU in %, median [max] over every run used. Tiles, cells and probe checks: scripts/gpu_crossover/ (tiles.py,
# cells.py, analyze.py; mkresult.py assembles this file). The run folders with the probe files are not published.

# 2. Where the GPU overtakes the CPU. There is no single size. The GPU is ahead in every round from 1.7 M cells on the
# notch filter, 2.4 M on the GCPW line and 2.9 M on the patch antenna (medians x1.10-1.52 from there, x1.25-1.52 from
# 3.1 M cells on); the medians cross for the last time at about 0.66, 1.45 and 1.91 M cells. Below that the two engines
# are within x0.89-1.23 of each other and the side depends on the model: the GPU leads on the GCPW line at 0.11-0.42 M
# cells (x1.03-1.23), trails on the notch filter (x0.89 at 0.27 M) and changes sides on the patch antenna (x0.94-1.11 up
# to 1.85 M). On grids that small the session moves the ratio as well (section 5).
# crossover patch antenna: the GPU is faster at every size from 2.864 M cells up (measured to 7.863 M); the last crossing is at about 1.91 M cells, between 1.849 (x0.993) and 2.864 M (x1.100), log-linear between the two medians; all crossings: CPU ahead above ~0.15 M (between 0.104 and 0.179 M), GPU ahead above ~0.32 M (between 0.295 and 0.426 M), CPU ahead above ~0.54 M (between 0.426 and 0.619 M), GPU ahead above ~1.91 M (between 1.849 and 2.864 M)
# crossover notch filter: the GPU is faster at every size from 0.818 M cells up (measured to 5.247 M); the last crossing is at about 0.66 M cells, between 0.503 (x0.974) and 0.818 M (x1.020), log-linear between the two medians
# crossover GCPW line: the GPU is faster at every size from 2.379 M cells up (measured to 5.057 M); the last crossing is at about 1.45 M cells, between 1.417 (x0.993) and 2.379 M (x1.167), log-linear between the two medians; all crossings: CPU ahead above ~0.73 M (between 0.645 and 1.417 M), GPU ahead above ~1.45 M (between 1.417 and 2.379 M)
# every round patch antenna: the GPU ahead in every round used at every size from 2.864 M cells (x1.035 or more); the next smaller point 1.849 M: x0.993 [0.983-1.006]
# every round notch filter: the GPU ahead in every round used at every size from 1.722 M cells (x1.108 or more); the next smaller point 0.818 M: x1.020 [0.934-1.031]
# every round GCPW line: the GPU ahead in every round used at every size from 2.379 M cells (x1.124 or more); the next smaller point 1.417 M: x0.993 [0.981-1.009]

# 3. Why the GPU's lead narrows on small grids, or turns into a loss (the c3 columns of section 1):
# (a) It waits for the CPU. Between IterateTS calls the CPU records the probes and evaluates the dumps while the GPU
#     idles ("outside"), and starting and finishing a call's command buffers leaves it idle too ("gaps"): 0.30-0.50 ms
#     per call on the smallest grids. On the patch antenna at scale 1 (the patch tutorial) a call ends every 31 steps,
#     at the nf2ff dumps, and holds 1.27 ms of GPU work, so the GPU is busy 81 % of the loop (79-82 % per run here,
#     73-79 % in the later runs of section 5); 94 % at 0.62 M cells, 98-99 % from 4.2 M. On the patch antenna, up to
#     0.62 M cells, its rate over busy time alone (GPU-only, 2413-2898 MC/s) is above the CPU's at every point
#     (1766-2825): on those grids the waiting decides. The notch filter and the GCPW line end a call every 81-750 steps
#     and keep the GPU busy 97-99 % at every size.
# (b) Its own rate is lower on small grids: GPU-only 1959 MC/s on the notch filter at 0.27 M cells against 3239 at 5.2
#     M, 1799-1956 on the GCPW line at 0.11-0.16 M against 3053 at 5.1 M. A dispatch there has few tiles for the 10 GPU
#     cores (notch filter at 0.27 M: 75-96 tiles of 256 threads; GCPW line at 0.11 M: 18-30) and short columns (4
#     z-vectors), and the edge work makes up more of the cells (the 8-cell PML and the Mur faces on the notch filter,
#     the conducting sheets and the Mur faces on the GCPW line). These causes were not separated; the patch antenna at
#     0.10 M cells (16-25 tiles of 256 threads, 12 z-vectors) ran 2510 MC/s over busy time.
# (c) The CPU is at its best in the middle of the range: 1573-2208 MC/s at 0.10-0.27 M cells, 2570-3003 at 0.62-1.85 M,
#     above the 2273 MC/s the cores reach from DRAM (paper, section "Where the ceiling is": one independent sub-grid per
#     thread, 111 GB/s at 49 B per cell), presumably because the caches then carry part of the traffic (not measured),
#     and 1919-2263 at 4.2-7.9 M cells, at or below that ceiling, while the GPU runs 2818-3220 there.
#
# 4. Checks
# checks: every CPU run (4 and 8 threads, every round) identical to the CPU reference (8 threads, round 0)
# GPU port probes against the CPU reference (8 threads, round 0; no FTZ in either), every GPU run used: max 1.7e-06 relative (bench.py's per-file max|v - v_ref| / max|v_ref|) over the files whose reference peak is a normal float
#   notch filter s2.5: port_it_2A (CPU peak 1.7e-39, GPU peak 0.0e+00), port_it_2B (CPU peak 5.6e-39, GPU peak 0.0e+00), port_ut_2A (CPU peak 1.8e-40, GPU peak 0.0e+00), port_ut_2B (CPU peak 6.4e-40, GPU peak 0.0e+00), port_ut_2C (CPU peak 2.2e-39, GPU peak 0.0e+00): subnormal on the CPU because the wave has not reached the port in this run; the GPU flushes subnormals to zero, so bench.py's ratio is 1 there by construction
# bench.py's own figure, all files: max 1.0e+00 relative
# TIMING=1 vs plain GPU (c3/c2, median of the per-point medians): x1.000 [0.984-1.026]
#
# 5. Run length and session: the patch tutorial (scale 1, 0.104 M cells) at the bench's 10 500 steps (the speed table's
# count, x0.93 there) and at the sweep's 36 500, paired in one session four hours after the sweep's point (16:32-16:37,
# others 0.3-0.7 cores), each twice; configs c0 multithreaded:8, c1 metal-diamond, c2 metal-diamond with TIMING=1.
#   10 500 steps: x0.929 [0.912-0.956] and x0.907 [0.892-0.948]; CPU 1887 and 1926 MC/s, GPU 1740 and 1735.
#   36 500 steps: x0.972 [0.929-0.973] and x0.953 [0.937-0.978]; CPU 1910 and 1904 MC/s, GPU 1852 and 1819.
#   The sweep's point (36 500 steps, 12:29-12:37): x1.107 [1.090-1.169]; CPU 1766, GPU 1956.
#   TIMING runs (per run): busy 74-79 % at 10 500 steps and 73-76 % at 36 500 (the sweep's 79-82 %); GPU-only 2184-2254
#   and 2421-2465 MC/s (sweep 2443-2515); outside 10-14 % and 12-15 % (sweep 8-10 %); gaps 11-12 % in all.
# So the run length moves this ratio by about 4 % (the GPU's own rate is 10 % lower in the shorter runs), and the session
# by 14-16 % (in the later session the CPU ran 8 % faster, and the CPU's work between the GPU's calls took longer, so the
# GPU waited more): on grids this small the two engines are close, and which one leads depends on the session.
